# Chapter 1 — Knowledge check answers

1. **Schema change between `Prepare` and `Step`.** `sqlite3_prepare_v2` (`prepare.c:937-954`) passes `SQLITE_PREPARE_SAVESQL` to `sqlite3LockAndPrepare`, which saves the original SQL text on the prepared statement (`sqlite3VdbeSetSql` at `prepare.c:795`). When `sqlite3_step` (`vdbeapi.c:919-966`) runs the statement, `OP_Transaction` (`vdbe.c:4102-4201`) compares the database file's schema cookie against the cookie compiled into the bytecode (`P3`), finds a mismatch, and expires the statement with `SQLITE_SCHEMA`. `sqlite3_step` catches `SQLITE_SCHEMA` in a loop (up to `SQLITE_MAX_SCHEMA_RETRY` = 50 times), calls `sqlite3Reprepare` to recompile from the saved SQL text, resets the statement, and steps it again automatically.

2. **`pwrite64` calls on `t.db` in rollback mode vs WAL mode.**
   - **Rollback mode (`journal_mode=delete`):** 2 `pwrite64` calls hit `t.db`: `off=0 len=4096` (page 1, updated change counter and version-valid-for) and `off=4096 len=4096` (page 2, table `t`'s leaf page holding the new row). Before those writes, SQLite journals the original images of both pages into `t.db-journal` and syncs the journal and directory.
   - **WAL mode (`journal_mode=wal`):** 0 `pwrite64` calls hit `t.db`. Instead, SQLite writes the 32-byte WAL header (`t.db-wal off=0 len=32`), syncs `t.db-wal` and `.`, appends frame 1's 24-byte header (`off=32 len=24`) and page 2's 4,096-byte image (`off=56 len=4096`) to `t.db-wal`, and syncs `t.db-wal`. Page 2's new bytes reach `t.db` only later during a checkpoint.

3. **Extra syscalls in the Go driver's twin check.** `modernc.org/sqlite` links `modernc.org/libc` (`v1.77.1`), whose `open()` wrapper is translated from musl and issues an explicit `fcntl(fd, F_SETFD, FD_CLOEXEC)` after opening a file with `O_CLOEXEC`. SQLite's C build relies on the `O_CLOEXEC` flag directly in `robust_open`. That produced 2 extra `fcntl F_SETFD` calls in rollback mode (for `t.db-journal` and `.`) and 1 in WAL mode (for `.`). `F_SETFD` only sets the close-on-exec flag on a process-local file descriptor; it writes nothing to disk and touches no POSIX byte-range locks. Every read, write, sync, lock, open, unlink, and close matched identically, and both builds produced byte-identical database files.

4. **Connection sessions in WAL mode vs rollback mode.** In WAL mode, only 2 bytes differed in the entire file—page 1 bytes `27` and `95`—which are the low bytes of the 4-byte file change counter (bytes 24–27) and the matching version-valid-for field (bytes 92–95). In WAL mode, `pagerWalFrames` writes `dbFileVers + 1`, but `dbFileVers` is refreshed from storage only when page 1 is read into the cache, not after a WAL commit. One long-lived connection therefore writes the same counter value across all 7 commits, while opening one connection per step re-reads page 1 and increments it on each session. In rollback mode, the change counter increments on every commit regardless of how many connections are opened, so both builds performed 7 commits and produced `identical` files.

5. **Transaction batching with `secure_delete=ON` vs `secure_delete=OFF` in WAL mode.** Because all steps ran on one WAL connection, the header change counter did not depend on commit count. With `secure_delete=OFF`, deleting rows in step 3 that were inserted in step 2 left stale deleted bytes inside unused regions of B-tree leaf pages (the unallocated gap between the cell-pointer array and the cell content area, plus freeblocks)—specifically 357 bytes on page 24 and 1,207 bytes on page 28—and merging steps `2+3` and `4+5` changed which stale bytes remained. Enabling `secure_delete=ON` zeroes freed space inside B-tree pages and freelist leaves, eliminating those history-dependent bytes so both batchings produced `identical` files.
