## Scope and Scaling Notes

- **Chunk boundary:** Attacks cover the service core (`s3store`, `faultstore`, `fence`, `catalog`, `bounds`, `node`, `model`), `internal/walship/atrest.go` (`AdoptAtRest`), and experiment `10.1-one-writer`. Relocation and experiments `10.2–10.4` belong to chunk `ch10b`.
- **Scaling:**
  - `MOD-04` (independent 3-node / 5-epoch / multi-slot-stale-list model): exhaustive BFS to depth **6** plus **50,000** seeded random walks of length **80** (~4M steps), plus a 500-walk overwrite mutant control.
  - `MOD-05a` (`model.Explore` multi-seed invariance): **5** seeds at depth **10** plus **10,000** random walks of length **100**.
  - `FENCE-02` (real concurrency races): **8** concurrent goroutines × **20** rounds on SeaweedFS S3 `PutIfAbsent`, and **8** concurrent catalog handles × **25** rounds (200 total epochs) on shared SQLite `catalog.Claim`.
  - `FENCE-03a`: **16** concurrent `node.Claim` vs `node.Claim` rounds on SeaweedFS S3.
  - `CAT-05a` (standing resource bounds): scaled from 2,000 to **600** databases (37.5× `Capacity=16`, `DirStore`, copying a pre-built valid step-0 SQLite template on create and performing a real WAL write + `walship` cycle + LRU eviction on every database; 2,000 took ~6 min alone due to ~10,000 ext4 fsyncs) plus **50** databases rotated on real SeaweedFS S3 (`Capacity=4`).
  - `CAT-05b` (long segment chain memory probe): **180** in-place 256 KiB `StoreDurable` `UPDATE`s on 1 small open database (`Capacity=1`).
- **Cross-platform builds:** All four Go programs use only cross-platform Go/repo packages and compile cleanly under `GOOS=darwin GOARCH=arm64` and `GOOS=darwin GOARCH=amd64` with `CGO_ENABLED=0`.

### Group 2: `fencing-and-crashes` (`agent_work/ch10a/adversarial/fencing-and-crashes/main.go`)

| ID | Claim attacked | Method | What a BROKEN result would mean |
| --- | --- | --- | --- |
| `FENCE-01a` | A `SIGKILL`ed owner that restarts believing it still owns the database cannot get writes accepted after a takeover (10.1). | Kill real node process `a` after takeover by `b`, restart `a` with its `epoch 1` belief file intact, send `write store-durable` and `write local-durable`. | Either write was accepted, the belief file remained on disk, or S3 lineage was modified. |
| `FENCE-01b` | A `SIGKILL`ed owner with unshipped `LocalDurable` commits cannot ship them after a takeover and restart (10.1). | Commit `LocalDurable` on `a`, `SIGKILL` `a`, take over on `b`, restart `a`, and send `ship`. | `a` shipped its unshipped local commit or was not fenced during `openDatabase`. |
| `FENCE-01c` | A restarted stale owner whose first store listing hides the new owner's fence (`stale-list:/log/:1`) still cannot get any segment accepted in S3 (10.1). | Restart killed stale owner `a` with `stale-list` hiding `b`'s fence; send `write store-durable` (db-c1) and `write local-durable` + `ship` (db-c2). | Stale `a` got any object accepted into S3 despite the stale listing. |
| `FENCE-01d` | A process crash between a fence `PutIfAbsent` and writing the `.owner` belief file is safely recoverable by the next `Claim` (build-notes line 328). | Inject `crash-after-put` on `a`'s `Claim`; restart `a` (verify no ownership belief) and have `b` `Claim` and write `StoreDurable`. | `a` retained a bogus belief or `b` failed to restore slot 1, fence at slot 2, and continue cleanly. |
| `FENCE-02` | SeaweedFS `s3store.PutIfAbsent` is atomic and exclusive under real concurrency, and SQLite `catalog.Claim` hands out unique epochs under concurrent handles. | Race 8 goroutines × 20 rounds on `s3store.PutIfAbsent` and 8 independent catalog handles × 25 rounds on `catalog.Claim`. | More than one S3 put succeeded, bytes were torn, or `catalog.Claim` produced duplicate epochs or `SQLITE_BUSY` errors. |
| `FENCE-03a` | Concurrent `node.Claim` races on real SeaweedFS S3 preserve a single valid lineage and never leave a failed `Claim` holding ownership. | Run 16 rounds of concurrent `a.Claim` vs `b.Claim` on real SeaweedFS S3; run `fence.Audit` and inspect `Owned(id)` on any failed `Claim`. | A lineage broke under concurrent claims, or a `Claim` that returned an error left `n.Owned(id) == true`. |
| `FENCE-03b` | Deterministic `Claim` vs `Claim` interleaving: `b` bumps the catalog epoch after `a`'s fence `PutIfAbsent` succeeds and before `a`'s `Catalog.RecordShipped` (`node.go:292`). | Use a post-put store hook to invoke `catB.Claim` before `nodeA`'s `RecordShipped`; inspect `Claim`'s error, `Owned(id)`, and `.owner` file. | `Claim` returned `catalog.ErrStaleEpoch` as an error while leaving `n.owned[id]` and `<id>.owner` set (inconsistent with `shipLocked`, which ignores `ErrStaleEpoch` after store acceptance). |
| `FENCE-04` | Active writer contention against `Claim` (`claimAttempts = 3`) preserves one-writer safety even if `Claim` exhausts retries. | Use a list hook so active owner `a` ships a `StoreDurable` commit right after each of `b`'s 3 `Claim` listings, then verify `a` can still write and `fence.Audit` is clean. | One-writer lineage broke or `a` was erroneously blocked before `b` placed a fence. |
| `FENCE-05` | `faultstore` faults (`fail-before-put`, `fail-after-put`, `partial-put`) and multi-slot stale listings (hiding 2 slots) preserve safety and integrity on real SeaweedFS S3. | Inject each fault on real `node.Write`/`node.Claim` against SeaweedFS; check recovery after `fail-before/after-put`, `ErrDamaged` rejection on `partial-put`, and 2-slot stale-list retry. | `fail-before/after` failed to recover cleanly, `partial-put` was accepted as a valid restore point, or 2-slot stale listing broke lineage. |
