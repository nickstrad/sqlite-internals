# Source inventory, chapters 1–4 (pinned SQLite 3.53.4)

Research note for the course OUTLINE (topic `source-inventory-a`, 2026-11-20). It maps the pinned
SQLite source to chapters 1–4 so the outline can cite real files, functions and lines.

**Pin.** Tag `version-3.53.4`, git `b09c88c14082339b66c7b7158d609a771e64ca69`, Fossil check-in
`bf7c7f30031888f4e796e429ab3978879485813aaca6f641c7b33e4e09459bcc`. Tree:
the pinned tree (`$SQLITE_SRC` or `_src/sqlite-3.53.4`). All paths below are relative to that tree, and all line numbers
come from that revision.

**How things were verified** (the "how" column in each table):

- **F**: a function, struct or opcode span measured by
  `agent_work/probes/source-inventory-a/funcspan.py`. Every span in this file is regenerated by
  `spans.sh` into `spans.txt`, which is committed next to it. Function ends are found by brace
  counting and cross-checked against the first column-0 `}`. Where the two disagree, the span was
  read by hand: `sqlite3VdbeExec` (opcode cases close at column 0), `sqlite3RunParser` (a literal
  defeats brace counting; its end is the column-0 `}`), and the one-liners `sqlite3_close_v2` and
  `sqlite3PcacheSize`.
- **G**: the cited line was found with `grep -n` (or `grep -n` limited to the caller's span). A call
  path hop "A→B @N" means line N, inside A's span, calls B.
- **R**: run against the installed CLI or library.
- **W**: fetched from sqlite.org on 2026-11-20 (`changes.html`, `chronology.html`, `fileformat2.html`,
  `schematab.html`). Every doc URL below returned HTTP 200.

Anything not verified is marked **UNVERIFIED**.

Consequences (all R):

- `PRAGMA vdbe_trace=1` is silently a no-op in both builds. `tool/mkpragmatab.tcl:94-98` gates
  `vdbe_trace` (and vdbe_listing, vdbe_debug, vdbe_addoptrace, parser_trace) on `defined(SQLITE_DEBUG)`.
- The CLI's `.iotrace` returns "unknown command". It is compiled only under `SQLITE_ENABLE_IOTRACE`
  (`src/shell.c.in:10023-10024`; the IOTRACE macro is at `src/sqliteInt.h:5828-5831`).
- `.scanstats on` prints "not available in this build".
- The CLI `-vfstrace` flag works. It includes `ext/misc/vfstrace.c` (`src/shell.c.in:301`) and is
  registered at `src/shell.c.in:13193`/`13332`; it printed `xOpen`, `xFileControl(MMAP_SIZE)`, and
  so on. It works with no special build.
- `.stats on` prints pager cache hit/miss/write/spill counts, lookaside, "Pcache Overflow Bytes",
  and the read()/write() syscall counts. `.dbinfo` decodes the 100-byte header (it showed "file
  change counter: 2", "software version: 3053004").
- `bytecode()`, `tables_used()`, `sqlite_dbpage` and `dbstat` all work in both builds.
- `sqlite3_stmt_explain` is exported by the .so (`nm -D`).

### 1.2 Verified call paths

**Prepare** (each step names the line that makes the call):

1. `sqlite3_prepare_v2` calls `sqlite3LockAndPrepare` at prepare.c:950.
2. `sqlite3LockAndPrepare` calls `sqlite3BtreeEnterAll` at :856, then `sqlite3Prepare` at :861.
3. `sqlite3Prepare` calls `sqlite3RunParser` at :779 (the copy-of-SQL branch) or :786.
4. `sqlite3RunParser` calls `sqlite3GetToken` at tokenize.c:646 and `sqlite3Parser(pEngine, …)` at
   :713. The parser engine is created at :631/:633.
5. The Lemon reductions in parse.y call `sqlite3Select` (:525), `sqlite3Insert` (:1084), and so on.
   `sqlite3Select` calls `sqlite3WhereBegin` at select.c:8292.
6. On end of command, parse.y:176 calls `sqlite3FinishCoding`. That function emits OP_Halt
   (build.c:193) and OP_Transaction (:211), then calls `sqlite3VdbeMakeReady` (:273).
7. Back in `sqlite3Prepare`, `schemaIsValid` runs at prepare.c:803.

**Step:**

1. `sqlite3_step` calls `sqlite3Step` at vdbeapi.c:930. If the result is SQLITE_SCHEMA, it calls
   `sqlite3Reprepare` (:933).
2. `sqlite3Step` calls `sqlite3VdbeList` at :864 when the statement is an EXPLAIN, otherwise
   `sqlite3VdbeExec` at :869.
3. `sqlite3VdbeExec` dispatches each opcode through `switch(pOp->opcode)` at vdbe.c:1014.

**VDBE → B-tree → pager → VFS, for a read:**

1. `OP_Transaction` calls `sqlite3BtreeBeginTrans` at vdbe.c:4128. That function (btree.c
   3805–3826) wraps `btreeBeginTrans`.
2. `btreeBeginTrans` loops on `lockBtree` at :3711. For write transactions it calls
   `sqlite3PagerBegin` (:3717) and, for an empty file, `newDatabase` (:3719).
3. `lockBtree` calls `sqlite3PagerSharedLock` at :3290 and `btreeGetPage(…,1,…)` at :3292.
4. `OP_OpenRead` calls `sqlite3BtreeCursor` at vdbe.c:4453.
5. `OP_Rewind` calls `sqlite3BtreeFirst` at :6394. `sqlite3BtreeFirst` calls `moveToRoot` at
   btree.c:5693, and `moveToRoot` calls `getAndInitPage` at :5586.
6. `getAndInitPage` calls `sqlite3PagerGet` at :2394, then `btreeInitPage` at :2402.
7. `sqlite3PagerGet` calls `pPager->xGet` at pager.c:5782/:5790. `setGetterMethod` (:1045) sets
   `xGet` to `getPageError`, `getPageMMap` or `getPageNormal` (:1047–1053).
8. `getPageNormal` calls `sqlite3PcacheFetch` at :5598. On a miss it calls `readDbPage` at :5666,
   and `readDbPage` calls `sqlite3OsRead` at :3087 (or `sqlite3WalReadFrame` at :3082).
9. `OP_Column` calls `sqlite3BtreePayloadFetch` at vdbe.c:3043, then `sqlite3VdbeSerialGet` at
   :3197.
10. `OP_Next` calls `sqlite3BtreeNext` at :6523.

**Write and commit:**

1. `OP_Insert` calls `sqlite3BtreeInsert` at vdbe.c:5816. Inside it, `sqlite3PagerWrite` is called
   at btree.c:9614 and `insertCellFast` at :9656 (details in Chapter 3).
2. `OP_Halt` calls `sqlite3VdbeHalt` at :1354, which calls `vdbeCommit` at vdbeaux.c:3421.
3. `vdbeCommit` calls `sqlite3BtreeCommitPhaseOne` at :3005. That calls `sqlite3PagerCommitPhaseOne`
   at btree.c:4330, which calls `syncJournal` (pager.c:6658), `pager_write_pagelist` (:6666/:6696)
   and `sqlite3PagerSync` (:6719).
4. `pager_write_pagelist` calls `sqlite3OsWrite` at :4527. `syncJournal` calls `sqlite3OsSync` at
   :4404/:4416. `sqlite3PagerSync` calls `sqlite3OsSync` at :6453.
5. Phase two: `vdbeCommit` calls `sqlite3BtreeCommitPhaseTwo` at vdbeaux.c:3020. That calls
   `sqlite3PagerCommitPhaseTwo` (btree.c:4416), which calls `pager_end_transaction` (pager.c:6784).
   The journal is deleted, truncated or zeroed at :2090/:2104/:2120.

**Finalize:** `sqlite3_finalize` calls `sqlite3VdbeReset` at vdbeapi.c:118. `sqlite3VdbeReset` calls
`sqlite3VdbeHalt` (vdbeaux.c:3598) if the statement is still running, then `sqlite3_finalize` calls
`sqlite3VdbeDelete` at vdbeapi.c:119.

**EXPLAIN:**

1. parse.y:173–174 sets `pParse->explain` to 1 or 2.
2. `sqlite3Step` sees the flag and calls `sqlite3VdbeList` at vdbeapi.c:864.
3. EXPLAIN QUERY PLAN rows come from the OP_Explain nodes that `sqlite3WhereExplainOneScan` and
   `sqlite3VdbeExplain` emit.
4. When a statement is reprepared, prepare.c:703 copies its explain mode across with
   `sqlite3_stmt_isexplain`.

### 2.2 Verified call paths

**Open and validate the header:**

1. `sqlite3BtreeOpen` (2532–2825) opens the pager and reads the first 100 bytes.
2. On the first transaction, `btreeBeginTrans` calls `lockBtree` at :3711.
3. `lockBtree` takes the shared lock (`sqlite3PagerSharedLock`, :3290), fetches page 1
   (`btreeGetPage`, :3292), then checks the size, the magic (:3314) and the field checks listed in
   2.1.
4. If the database is empty and the transaction is a write, `btreeBeginTrans` calls `newDatabase`
   at :3719. `newDatabase` writes the header (:3524–3545) and calls `zeroPage` (:3536).

**Page parse:** `getAndInitPage` calls `btreeInitPage` at :2402, which calls `decodeFlags` at :2234.
`decodeFlags` installs `xParseCell`/`xCellSize` (:2040–2080).

**Record read:**

1. `OP_Column` calls `sqlite3BtreePayloadFetch` at vdbe.c:3043.
2. It reads the header size with `sqlite3GetVarint32` (:3051) and each serial type (:3130), then
   decodes the value with `sqlite3VdbeSerialGet` (:3197).
3. Large values take a different branch: `vdbeColumnFromOverflow` (:3245) calls
   `sqlite3VdbeMemFromBtree` (:785), which reaches `accessPayload`. `accessPayload` calls
   `getOverflowPage` (:5251) and then either `sqlite3OsRead` (DIRECT_OVERFLOW_READ, :5287) or
   `sqlite3PagerGet` (:5295).

**Record write:** `OP_MakeRecord` writes the header length (`sqlite3PutVarint`, :3718) and each
serial type (:3768).

**Change counter:**

1. Commit-phase-one calls `pager_incr_changecounter` at pager.c:6620/6624/6636, which calls
   `pager_write_changecounter` at :6409.
2. In the other path, `pager_write_pagelist` calls `pager_write_changecounter` when page 1 is in
   the dirty list (:4522).

### 2.7 Version notes

- In-header database size (offset 28) is trusted only when version-valid-for (92) equals the change
  counter (24), since 3.7.0. Source: btree.c:3300 and fileformat2.html (W).
- Default page size went from 1024 to 4096, and the default cache_size from 2000 to -2000, in
  3.12.0 (changes.html; pgszchng2016.html) (W). The installed builds have DEFAULT_PAGE_SIZE=4096
  (R).
- `sqlite_master` is now `sqlite_schema` (preferred name), with the legacy name kept
  (sqliteInt.h:1246–1248). The release that introduced the new name is **UNVERIFIED**: it was not
  found by grep of changes.html. The usual citation is 3.33.0.
- `sqlite_dbpage` vtab added in 3.21.0. INSERT can resize the file since 3.47.0. The dbstat
  aggregated mode came in 3.31.0 (W).
- The payload fractions 64/32/32 have been required to be fixed "as of version 3.6.0"
  (btree.c:3360–3363).
- Changelog (W, 3.54.x): the CLI gained a `.diskused` command and `sqlite3_analyzer` is deprecated.
  This is **after** our pin, so do not tell learners to use `.diskused`.

### 3.2 Verified call paths

**Insert:**

1. `OP_Insert` calls `sqlite3BtreeInsert` at vdbe.c:5816.
2. `sqlite3BtreeInsert` calls `fillInCell` (:9601). If the payload is large, `fillInCell` calls
   `allocateBtreePage` (:7212).
3. `sqlite3BtreeInsert` then calls `sqlite3PagerWrite` (:9614) and `insertCellFast` (:9656).
4. `insertCellFast` calls `allocateSpace` (:7472). `allocateSpace` tries `pageFindSlot` (:1863) and
   otherwise calls `defragmentPage` (:1885). If the cell does not fit, it is queued as an overflow
   cell.
5. `sqlite3BtreeInsert` then calls `balance` (:9683). `balance` dispatches to one of three
   functions:
   - `balance_deeper` (:9158), when the root overflows;
   - `balance_quick` (:9206), for appends;
   - `balance_nonroot` (:9228), otherwise. `balance_nonroot` calls `editPage` (:8942), which may
     call `rebuildPage` (:7979).

**Delete and reuse:**

1. `sqlite3BtreeDelete` expands the `BTREE_CLEAR_CELL` macro at :9947. The macro calls
   `clearCellOverflow` (:7056), which calls `freePage2` (:7035) for each overflow page.
2. It calls `dropCell` at :9948, and `dropCell` calls `freeSpace` (:7292).
3. It calls `balance` at :10007/:10016. During balancing, `balance_nonroot` frees surplus siblings
   with `freePage` (:9000).
4. A later `allocateBtreePage` takes pages back off the freelist trunk (:6590–6676).

**Autovacuum at commit:**

1. `sqlite3BtreeCommitPhaseOne` calls `autoVacuumCommit` at :4320.
2. `autoVacuumCommit` calls `incrVacuumStep` at :4262 in a loop.
3. `incrVacuumStep` calls `relocatePage` at :4116.
4. Back in `sqlite3BtreeCommitPhaseOne`, `sqlite3PagerTruncateImage` (:4327) shrinks the file.

**Incremental vacuum:** OP_IncrVacuum calls `sqlite3BtreeIncrVacuum` at vdbe.c:8181, which calls
`incrVacuumStep` at btree.c:4184.

**Integrity check:** OP_IntegrityCk calls `sqlite3BtreeIntegrityCheck` at vdbe.c:7284. That calls
`checkTreePage` at :11249, which recurses (:10950, :11015).

### 4.2 Verified call paths

**State transitions (rollback-journal mode):**

1. OPEN to READER: `sqlite3PagerSharedLock` (5300–5507). It may replay a hot journal on the way
   (:5328, :5402). It sets `eState = PAGER_READER` at :5503.
2. READER to WRITER_LOCKED: `sqlite3PagerBegin` takes the RESERVED lock (:6002) and sets the state
   at :6018.
3. WRITER_LOCKED to WRITER_CACHEMOD: on the first `pager_write`, `pager_open_journal` (:6121)
   writes the journal header (:5935) and sets the state (:5945).
4. WRITER_CACHEMOD to WRITER_DBMOD: set at the end of `syncJournal` (pager.c:4438). The journal
   must be synced before the database file is written, whether in commit or in `pagerStress`;
   `pager_write_pagelist` asserts WRITER_DBMOD (:4480).
5. To WRITER_FINISHED: at the end of `sqlite3PagerCommitPhaseOne` (:6727).
6. Back to READER: `pager_end_transaction` (:2176).
7. To ERROR: `pager_error` (:1968). To OPEN: `pager_unlock` (:1875/:1912/:1925).

**Fetch:**

1. `sqlite3PagerGet` calls `xGet` (:5782).
2. With `getPageNormal`, it calls `sqlite3PcacheFetch` (:5598).
   - `sqlite3PcacheFetch` calls `pcache2.xFetch` (pcache.c:427). With the default cache, that is
     `pcache1Fetch`, which calls `pcache1FetchNoMutex` (:1068), which calls `pcache1FetchStage2`
     (:1026). That either recycles an LRU page (:902–908) or calls `pcache1AllocPage` (:922), which
     calls `pcache1Alloc` (:451).
   - If no page is available, `getPageNormal` calls `sqlite3PcacheFetchStress` (pager.c:5601).
     That calls `xStress`, which is `pagerStress` (pcache.c:481). `pagerStress` calls `syncJournal`
     (:4710) and `pager_write_pagelist` (:4716).
3. On a miss, `getPageNormal` calls `readDbPage` (:5666), and `readDbPage` calls `sqlite3OsRead`
   (:3087).
4. With mmap, `getPageMMap` calls `sqlite3OsFetch` (:5728). On unix that is `unixFetch`, which
   calls `unixMapfile` (:5728).

**Write:**

1. `sqlite3PagerWrite` calls `pager_write` (:6294).
2. `pager_write` calls `pager_open_journal` (:6121), then `sqlite3PcacheMakeDirty` (:6128), then
   `pagerAddPageToRollbackJournal` (:6140).

**Commit:** the order is change counter, then journal sync, then db write, then db sync, then
journal finalize.

1. `sqlite3PagerCommitPhaseOne` calls `pager_incr_changecounter` (:6620), `syncJournal` (:6658)
   (which calls `sqlite3OsSync` at :4404/:4416), `pager_write_pagelist` (:6666) (which calls
   `sqlite3OsWrite` at :4527), and `sqlite3PagerSync` (:6719) (which calls `sqlite3OsSync` at
   :6453).
2. `sqlite3PagerCommitPhaseTwo` calls `pager_end_transaction` (:6784), which deletes, truncates or
   zeroes the journal (:2090/:2104/:2120).

**Hot-journal recovery:**

1. `sqlite3PagerSharedLock` calls `hasHotJournal` (:5328), which checks `sqlite3OsAccess` (:5196)
   and `sqlite3OsCheckReservedLock` (:5209).
2. It then takes the EXCLUSIVE lock with `pagerLockDb` (:5354) and calls `pager_playback` (:5402).
3. `pager_playback` calls `readJournalHdr` (:2911) and `pager_playback_one_page` (:2970), which
   writes each page back with `sqlite3OsWrite` (:2441).

**Memory budget:**

- PRAGMA cache_size (pragma.c:882) calls `sqlite3BtreeSetCacheSize` (:889), which calls
  `sqlite3PagerSetCachesize`. That calls `sqlite3PcacheSetCachesize` (pager.c:3565), which calls
  `xCachesize` (pcache.c:866). With the default cache this is `pcache1Cachesize`, which calls
  `pcache1EnforceMaxPage` (:829).
- `sqlite3_soft_heap_limit64` sets `nearlyFull` (malloc.c:114). `pcache1UnderMemoryPressure` reads
  it through `sqlite3HeapNearlyFull` (pcache1.c:524), and `pcache1FetchStage2` then recycles pages
  instead of allocating (:891/:902).

**Stats:** `sqlite3_db_status64` handles CACHE_USED by calling `sqlite3PagerMemUsed` (status.c:273),
and CACHE_HIT/MISS/WRITE/SPILL by calling `sqlite3PagerCacheStat` (:375). The `aStat` counters are
incremented at pager.c:5618 (HIT), :5665 (MISS), :4539/:3262/:6418 (WRITE) and :4689 (SPILL).

### 4.7 Version notes

- 3.12.0: default cache_size changed from 2000 pages to -2000 (KiB), and the page size from 1024 to
  4096 (W). Labs must state that cache_size is negative = KiB (`numberOfCachePages`, pcache.c
  277–292).
- 3.51.0 added `SQLITE_DBSTATUS_TEMPBUF_SPILL` (W). It is present at the pin (status.c:390).
  Earlier drivers' constant tables may lack it.
- 3.23.0 added `SQLITE_DBSTATUS_CACHE_SPILL`. 3.7.12 added `CACHE_WRITE`. 3.7.9 added
  `CACHE_HIT`/`CACHE_MISS` (W).
- 3.31.0 added `sqlite3_hard_heap_limit64` and PRAGMA hard_heap_limit (W).
- pager.c:4199 notes behavior "prior to version 3.8.3, it never checked". pager.c:1650 notes
  "versions of SQLite prior to 3.5.8 set the page-size field of the [journal header]" differently.
  These are minor and worth a footnote at most.
